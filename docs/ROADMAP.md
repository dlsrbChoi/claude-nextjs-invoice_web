# 노션 기반 견적서 관리 시스템 고도화 로드맵

MVP로 완성된 공개 조회 전용 견적서 시스템에, **발행자를 위한 관리자 견적서 목록**과 **링크 공유 편의성**을 더하고 **표 가시성 결함**을 해결하는 확장 단계

## 개요

MVP(v1.0)는 "클라이언트가 고유 URL로 견적서를 조회하고 PDF로 저장한다"는 흐름을 완성했습니다. 그러나 **발행자 본인의 워크플로우는 전적으로 노션 안에 남아 있습니다.** 발행자는 견적서를 보내려면 노션을 열고, 페이지를 찾고, ID를 복사하고, URL을 손으로 조립해야 합니다.

이번 고도화(v2.0)는 그 간극을 메웁니다:

- **관리자 견적서 목록 (F020)**: 발행한 견적서를 한 화면에서 조회. 노션 데이터베이스 쿼리 기반의 신규 데이터 경로
- **링크 복사 (F021)**: 목록의 각 행에서 클라이언트 공유 URL을 클릭 한 번으로 복사
- **표 가시성 개선 (F022)**: 라이트 모드에서 사실상 보이지 않는 견적서 항목 테이블의 대비 결함 해결

### 이번 단계의 전제

- **재구축이 아닌 확장**입니다. 기존 라우트, 타입, 컴포넌트, 파서를 그대로 재사용하며 신규 코드는 최소화합니다.
- **공개 조회 경로(`/invoice/[notionPageId]`)의 동작은 변경하지 않습니다.** Task 503(표 개선)만이 이 경로에 영향을 주며, 이는 시각적 개선에 한정됩니다.
- **관리자 "인증"은 이번 범위가 아닙니다.** 상세 근거는 아래 "보안 경계" 절을 참조하세요.

### 기술 스택 (MVP에서 변동 없음)

| 영역        | 기술                                             |
| ----------- | ------------------------------------------------ |
| 프레임워크  | Next.js 16 (App Router), React 19, TypeScript 5  |
| 스타일링    | TailwindCSS v4, shadcn/ui (base-nova), oklch     |
| 테마        | next-themes (라이트/다크/시스템)                 |
| 외부 API    | Notion API v1 (fetch 기반 클라이언트)            |
| 배포        | Vercel                                           |

**신규 의존성 없음.** 링크 복사는 브라우저 표준 `navigator.clipboard`, 토스트는 이미 설치된 `sonner`를 사용합니다.

### MVP에 존재하지 않아 신규 구축이 필요한 것

코드베이스 확인 결과, 다음은 **현재 전혀 없습니다.** 이것이 Phase 5의 실질적 작업량입니다.

- `NOTION_DATABASE_ID` 환경 변수를 사용하는 코드 (소스 전체에서 참조 0건)
- Notion **데이터베이스 쿼리**(`POST /v1/databases/{id}/query`) 호출 — 현재 `notion.ts`는 단일 페이지 조회(`GET /v1/pages/{id}`)만 수행
- `/admin` 계열 라우트 및 레이아웃

## 보안 경계 (착수 전 필독)

**관리자 목록은 인증 없이 배포하면 안 됩니다.** `/admin` 경로는 발행한 모든 견적서의 클라이언트명, 이메일, 금액을 노출합니다. MVP의 공개 조회 경로는 "URL을 아는 사람만 접근"이라는 전제가 성립했지만, 목록 화면은 그 전제를 깨뜨립니다 — 하나의 URL이 모든 견적서를 드러냅니다.

이번 로드맵은 **Task 507에서 최소한의 접근 제어를 필수 항목으로 포함**하며, 이는 프로덕션 배포의 선행 조건입니다. Phase 5를 로컬 개발 환경에서 진행하는 것은 안전하지만, **Task 507 완료 전까지 `/admin`을 Vercel 프로덕션에 배포하지 마세요.**

또한 클라이언트 이메일이 목록에 표시되므로, 화면 공유·스크린샷 상황을 고려해 Task 505에서 이메일 컬럼의 노출 정책을 결정합니다.

## 개발 워크플로우

1. **작업 계획**

- 기존 코드베이스를 학습하고 현재 상태를 파악
- 새로운 작업을 포함하도록 `docs/ROADMAP.md` 업데이트
- 우선순위 작업은 마지막 완료된 작업 다음에 삽입

2. **작업 생성**

- 기존 코드베이스를 학습하고 현재 상태를 파악
- `/tasks` 디렉토리에 새 작업 파일 생성
- 명명 형식: `XXX-description.md` (예: `501-admin-route.md`)
- 고수준 명세서, 관련 파일, 수락 기준, 구현 단계 포함
- **API/비즈니스 로직 작업 시 "## 테스트 체크리스트" 섹션 필수 포함 (Playwright MCP 테스트 시나리오 작성)**
- 예시를 위해 마지막 완료된 작업 참조. 예를 들어 현재 작업이 `504`라면 `503`과 `502`를 참조.
- 완료된 작업 예시는 체크된 박스와 변경 사항 요약을 포함함. 새 작업 문서는 빈 박스여야 하며 변경 사항 요약이 없어야 함.

3. **작업 구현**

- 작업 파일의 명세서를 따름
- 기능과 기능성 구현
- **API 연동 및 비즈니스 로직 구현 시 Playwright MCP로 테스트 수행 필수**
- 각 단계 후 작업 파일 내 단계 진행 상황 업데이트
- 구현 완료 후 Playwright MCP를 사용한 E2E 테스트 실행
- 테스트 통과 확인 후 다음 단계로 진행
- 각 단계 완료 후 중단하고 추가 지시를 기다림

4. **로드맵 업데이트**

- 로드맵에서 완료된 작업을 ✅로 표시

### Phase 6: 관리자 목록 데이터 연동 및 기능 완성

Phase 5의 골격 위에 실제 Notion 데이터베이스 쿼리를 연결합니다. Task 504가 데이터 경로를 열고, 505·506이 그 위에 UI와 상호작용을 얹습니다.

- **Task 504: Notion 데이터베이스 쿼리 기반 목록 조회 구현 (F020)** (우선순위)
  - `NOTION_DATABASE_ID` 환경 변수 도입 — `.env.example` 및 `docs/OPERATIONS_GUIDE.md`에 설정 절차 추가
  - `src/lib/notion.ts`에 `getInvoiceListFromNotion()` 신규 구현 — `POST /v1/databases/{id}/query` 호출
  - **기존 `parseInvoiceFromNotionPage()` 재사용** — 쿼리 결과의 각 `page` 객체는 단일 페이지 조회와 동일한 구조이므로 신규 파서를 작성하지 않음
  - **N+1 회피**: 목록에서는 항목(items) relation을 순회하지 않음. 총액은 노션의 `total_amount` property 값을 사용 (상세 화면만 항목을 로드)
  - 정렬 규칙 적용 — `issue_date` 내림차순(최신 발행 우선)을 기본값으로 쿼리 `sorts` 파라미터 구성
  - 페이지네이션 대응 — Notion API의 `start_cursor`/`has_more` 처리, `page_size` 기본 25건
  - `React.cache()` 및 `revalidate` 캐싱 전략을 기존 조회 경로와 일관되게 적용
  - 에러 처리 — 기존 `NotionAPIError` 계열 클래스 재사용, DB ID 미설정 시 `NotionConfigError`로 명확히 안내
  - 데이터베이스 미설정 상태에서도 앱이 크래시하지 않고 안내 화면으로 폴백

  **테스트 체크리스트 (Playwright MCP)**
