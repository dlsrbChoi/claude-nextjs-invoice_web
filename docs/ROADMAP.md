# 노션 기반 견적서 관리 시스템 v3.0 고도화 로드맵

단일 목록 화면에 머물러 있던 관리자 영역을, **좌측 네비게이션을 갖춘 종합 대시보드**로 확장하고 **이메일 공유·페이지네이션·신고 관리**를 더하는 단계

## 개요

v2.0은 발행자에게 "견적서 목록을 보고 링크를 복사한다"는 최소 워크플로우를 제공했습니다. 그러나 관리자 영역은 여전히 **`/admin` 단일 화면**이며, 화면 간 이동 수단이 없고, 견적서가 늘어나면 한 페이지에 전부 쏟아집니다. 공유 수단도 클립보드 복사 하나뿐입니다.

v3.0은 관리자 영역을 **여러 화면으로 구성된 하나의 제품**으로 재편합니다:

- **관리자 대시보드 (F030)**: 견적서 현황·클라이언트 요약·최근 활동을 한눈에 보여주는 진입 화면
- **좌측 메뉴 네비게이션 (F031)**: 대시보드/견적서/클라이언트/신고 간 이동 수단. 관리자 레이아웃의 구조적 기반
- **링크 복사 개선 (F032)**: v2.0의 복사 액션에 공유 URL 미리보기와 피드백 일관성을 보강
- **이메일 공유 (F033)**: 링크를 손으로 전달하는 대신, 클라이언트에게 직접 발송
- **페이지네이션 (F034)**: 이전/다음 버튼 기반. v2.0에서 이미 확보한 커서를 화면에 연결
- **신고 관리 (F035)**: 신고된 견적서를 조회하고 처리하는 운영 기능

### 이번 단계의 전제

- **재구축이 아닌 재편입니다.** 기존 라우트, 타입, 파서, `InvoiceListTable`, 클립보드 훅을 그대로 재사용합니다.
- **공개 조회 경로(`/`, `/invoice/[notionPageId]`)의 동작은 변경하지 않습니다.** v3.0의 모든 신규 화면은 `/admin` 하위에 위치합니다.
- **견적서 작성·수정은 여전히 노션에서 수행합니다.** 웹은 조회·공유·운영을 담당한다는 원칙을 유지합니다.
- **v2.0 인증에는 치명적 결함이 있으며, Task 601이 이를 선행 차단합니다.** 아래 "보안 경계" 절을 반드시 먼저 읽으세요.

## 보안 경계 (착수 전 필독)

### 🚨 최우선: v2.0 인증 우회 취약점

**현재 `/admin`은 사실상 인증되지 않은 상태입니다.** 코드 확인 결과:

- `src/app/api/auth/login/route.ts`는 세션 토큰을 `admin_${Date.now()}_${랜덤}` 형태의 **평문**으로 발급하며, 서버는 이 값을 어디에도 저장하지 않습니다.
- `src/middleware.ts`는 쿠키의 **존재와 비어 있지 않음만 검증**합니다(`if (!sessionCookie || !sessionCookie.value)`).

즉 공격자가 브라우저 콘솔이나 curl로 `admin_session=anything` 쿠키를 임의로 설정하면 **비밀번호 없이 전체 견적서의 클라이언트명·이메일·금액에 접근할 수 있습니다.** 이는 이론적 위험이 아니라 즉시 악용 가능한 결함입니다.

v3.0은 이메일 발송(대외 행위)과 신고 관리(운영 데이터)를 추가하므로 이 결함의 영향 범위가 커집니다. **Task 601을 Phase 1의 최우선 항목으로 배치하며, 완료 전까지 v3.0의 어떤 기능도 프로덕션에 배포하지 마세요.**

### 이메일 공유(F033)의 보안 요구사항

이메일 발송은 **서버가 제3자에게 능동적으로 메시지를 보내는 첫 기능**이므로 새로운 위험을 동반합니다. Task 613에서 다음을 필수 구현합니다.

- **오픈 릴레이 방지**: 수신자 주소를 클라이언트 입력에 전적으로 의존하지 않고, 노션에 등록된 해당 견적서의 `clientEmail`을 기본값으로 사용
- **발송 속도 제한**: 관리자 세션당 분·시간 단위 발송 횟수 제한 (스팸 발송 경로로 악용 차단)
- **헤더 인젝션 차단**: 수신자·제목 입력값에서 개행 문자(`\r`, `\n`) 제거
- **본문 이스케이프**: 사용자 입력이 HTML 템플릿에 삽입될 때 XSS 방지 이스케이프
- **API 키 서버 전용**: 이메일 서비스 키를 `NEXT_PUBLIC_` 접두사 없이 서버 환경 변수로만 관리
- **발송 이력 기록**: 누가·언제·누구에게 보냈는지 감사 가능하도록 기록

### 신고 관리(F035)의 보안 요구사항

- 신고 접수 경로가 공개라면 **비인증 스팸 유입**이 가능하므로, 접수 시 속도 제한과 봇 방지를 적용
- 신고 내용은 제3자가 작성한 **신뢰할 수 없는 입력**이므로, 관리자 화면 렌더링 시 반드시 이스케이프 처리 (저장형 XSS 차단)
- 신고 처리 액션(숨김·삭제)은 **인증된 관리자만** 수행 가능하며, 처리 이력을 남길 것

### 화면 노출 정책

대시보드와 클라이언트 목록은 클라이언트 이메일·금액을 한 화면에 집약합니다. 화면 공유·스크린샷 상황을 고려해 Task 608에서 **이메일 마스킹 여부**를 결정하고 문서화합니다.

## 개발 워크플로우

1. **작업 계획**

- 기존 코드베이스를 학습하고 현재 상태를 파악
- 새로운 작업을 포함하도록 `docs/ROADMAP.md` 업데이트
- 우선순위 작업은 마지막 완료된 작업 다음에 삽입

2. **작업 생성**

- 기존 코드베이스를 학습하고 현재 상태를 파악
- `/tasks` 디렉토리에 새 작업 파일 생성
- 명명 형식: `XXX-description.md` (예: `601-session-hardening.md`)
- 고수준 명세서, 관련 파일, 수락 기준, 구현 단계 포함
- **API/비즈니스 로직 작업 시 "## 테스트 체크리스트" 섹션 필수 포함 (Playwright MCP 테스트 시나리오 작성)**
- 예시를 위해 마지막 완료된 작업 참조. 예를 들어 현재 작업이 `604`라면 `603`과 `602`를 참조.
- 완료된 작업 예시는 체크된 박스와 변경 사항 요약을 포함함. 새 작업 문서는 빈 박스여야 하며 변경 사항 요약이 없어야 함.

3. **작업 구현**

- 작업 파일의 명세서를 따름
- 기능과 기능성 구현
- **API 연동 및 비즈니스 로직 구현 시 Playwright MCP로 테스트 수행 필수**
- 각 단계 후 작업 파일 내 단계 진행 상황 업데이트
- 구현 완료 후 Playwright MCP를 사용한 E2E 테스트 실행
- 테스트 통과 확인 후 다음 단계로 진행
- 각 단계 완료 후 중단하고 추가 지시를 기다림

4. **로드맵 업데이트**

- 로드맵에서 완료된 작업을 ✅로 표시

### 작업 완료 기준 (모든 Task 공통)

```bash
npm run check-all   # lint + format:check + typecheck
npm run build       # 프로덕션 빌드 검증
```

## 개발 단계

### Phase 1 (v3.0): 관리자 셸 골격 및 타입 정의

구조 우선 접근법에 따라 **라우트 골격 · 타입 · 레이아웃**을 먼저 완성합니다. 이 Phase가 끝나면 관리자 영역의 모든 화면을 클릭으로 돌아다닐 수 있으며(내용은 비어 있음), 이후 Phase는 각 화면을 독립적으로 채우기만 하면 됩니다.

**Task 601을 제외한 나머지는 서로 의존하지 않아 병렬 진행이 가능합니다.**

- **Task 601: 관리자 세션 검증 강화 및 인증 우회 차단** ✅ - 완료
  - **필수 이유**: 현재 미들웨어가 쿠키 존재 여부만 확인하여 임의 쿠키로 인증 우회가 가능 (보안 경계 절 참조)
  - `src/lib/auth.ts` 신규 생성 — HMAC 서명 기반 세션 토큰 발급·검증 함수 구현 (Node 내장 `crypto` 사용, 신규 의존성 없음)
  - `ADMIN_SESSION_SECRET` 환경 변수 도입 — `.env.example` 및 `docs/DEPLOYMENT.md`에 설정 절차 추가
  - 토큰 페이로드에 **만료 시각(exp)** 포함 — 서버가 쿠키 값만으로 유효성·만료를 판정할 수 있게 구성
  - `src/app/api/auth/login/route.ts` 수정 — 평문 토큰 발급을 서명 토큰 발급으로 교체
  - `src/middleware.ts` 수정 — 존재 여부 검증을 **서명 검증 + 만료 검증**으로 교체, 실패 시 `/login` 리다이렉트
  - **Edge 런타임 호환성 확인** — 미들웨어는 Edge에서 실행되므로 사용 API가 Edge에서 동작하는지 검증 (미지원 시 Web Crypto API로 대체)
  - 비밀번호 비교를 **타이밍 공격에 안전한 비교**로 교체 (`crypto.timingSafeEqual`)
  - 로그인 실패 시 응답 지연 또는 시도 횟수 제한으로 브루트포스 완화
  - `docs/SECURITY_VERIFICATION.md`에 세션 위조 차단 검증 항목 추가

  **테스트 체크리스트 (Playwright MCP)**
  - [ ] `admin_session=fake` 임의 쿠키 주입 후 `/admin` 접근 → 로그인 페이지로 차단되는지 확인 (**회귀 방지 핵심**)
  - [ ] 정상 로그인 → 발급된 쿠키로 `/admin` 접근이 정상 동작하는지 확인
  - [ ] 쿠키 값의 서명 부분을 1글자 변조 후 접근 → 차단되는지 확인
  - [ ] 만료된 토큰(exp 경과)으로 접근 → 로그인 페이지로 리다이렉트되는지 확인
  - [ ] 잘못된 비밀번호 → 401 및 에러 메시지 표시, 쿠키 미발급 확인

### Phase별 완료 정의 (Definition of Done)

- **Phase 1**: 인증 우회가 차단되고, 관리자 4개 라우트가 좌측 메뉴로 이동 가능하며, 모든 도메인 타입이 정의되어 빌드가 성공한다
- **Phase 2**: 대시보드·클라이언트·신고·이메일 모달이 더미 데이터로 완전히 동작하고, 반응형·대비 기준을 충족한다
- **Phase 3**: 모든 화면이 실제 데이터로 동작하고, 이메일 발송과 신고 처리가 보안 요구사항을 충족하며 프로덕션 배포가 가능하다
- **Phase 4**: 성능이 계측·최적화되고 운영 문서가 갱신되어 배포가 완료된다
